# استقرار Vercel، PostgreSQL و سرور داخلی

## معماری و محدودیت‌ها

`vercel.json` رابط Next.js را به frontend و مسیرهای `/api/*`، `/_health` و `/_ready` را به API کانتینری Go می‌فرستد. داده‌ها و نشست‌ها باید در PostgreSQL پایدار و قابل‌دسترس شبکه‌ای ذخیره شوند؛ فایل کانتینر و حافظهٔ آن پایدار نیستند. ورود Manus حذف شده است. ثبت‌نام عمومی بدون تأیید ایمیل انجام می‌شود و حساب بلافاصله فعال و قابل ورود است.

همهٔ کاربران **فعال** در نسخهٔ فعلی می‌توانند همهٔ پروژه‌های مشترک را ببینند و ویرایش کنند. نقش admin فقط به مدیریت کاربران دسترسی اضافه می‌کند؛ کنترل دسترسی تفکیکی پروژه، سیستم مالی، ممیزی و بازیابی خودکار رمز هنوز پیاده نشده‌اند. پیش از اطلاعات واقعی، دسترسی‌ها و backup/restore باید متناسب با نیاز شرکت بررسی شوند.

## Vercel و PostgreSQL

1. یک دیتابیس PostgreSQL پایدار، برای مثال Neon، بسازید و به پروژهٔ `multi-project-manager` متصل کنید. منطقه، شرایط طرح و محدودیت‌های آن را در ارائه‌دهنده بررسی کنید. `DATABASE_URL` باید در محیط production به سرویس API برسد؛ اگر Neon نام متفاوتی برای connection string قرار می‌دهد، آن را به `DATABASE_URL` نگاشت کنید. اتصال خارج از شبکهٔ خصوصی باید TLS فعال داشته باشد. URL و رمز را در Git یا متن عمومی نگذارید.
2. در تنظیمات Environment Variables برای محیط production و در صورت وجود، سرویس backend، مقادیر زیر را تنظیم کنید:
   - `DATABASE_URL`: رشتهٔ اتصال PostgreSQL پایدار.
   - `APP_ENV=production` و `PORT=8080`.
   - `PUBLIC_APP_ORIGIN`: دقیقاً مبدأ HTTPS عمومی که کاربران با آن کار می‌کنند، مانند `https://projects.example.com`؛ بدون مسیر و slash پایانی. درخواست‌های تغییردهنده از مبدأ دیگری رد می‌شوند؛ اگر چند دامنه دارید یکی را به دامنهٔ اصلی هدایت کنید.
   - `BOOTSTRAP_ADMIN_EMAIL` و `BOOTSTRAP_ADMIN_PASSWORD`: مشخصات مدیر اولیه فقط برای دیتابیس خالی. رمز باید ۴ تا ۷۲ بایت UTF-8 باشد. این متغیرها فقط server-side و محرمانه‌اند و نباید با `NEXT_PUBLIC_` شروع شوند.
3. سرویس را redeploy کنید. در نخستین شروع، مهاجرت‌ها با قفل تراکنشی اجرا و یک مدیر فعال ساخته می‌شود. هیچ ثبت‌نام‌کننده‌ای خودکار مدیر نمی‌شود. وقتی ورود مدیر تأیید شد، متغیرهای `BOOTSTRAP_ADMIN_EMAIL` و `BOOTSTRAP_ADMIN_PASSWORD` را از تنظیمات حذف و دوباره deploy کنید. راه‌اندازی مجدد رمز یا نقش حساب موجود را بازنویسی نمی‌کند.
4. با مدیر وارد شوید و یک حساب آزمایشی ثبت کنید؛ حساب ثبت‌نامی بلافاصله فعال و قابل ورود است. ایمیل تکراری پذیرفته نمی‌شود و رمز باید حداقل ۴ و حداکثر ۷۲ بایت باشد. ورود/خروج را بیازمایید. دادهٔ آزمایشی را صرفاً با اجازهٔ صاحب سیستم بسازید.
5. `/_health` زنده‌بودن فرایند را نشان می‌دهد؛ `/_ready` پس از موفقیت راه‌اندازی پاسخ می‌دهد. موفقیت build لزوماً به معنی سالم‌بودن اتصال دیتابیس، ورود یا دسترسی شبکه‌ای نیست. تنظیمات Deployment Protection ورسل نیز جدا از ورود اپلیکیشن‌اند.

برای میزبان‌های `*.neon.tech` اتصال TLS و بررسی نام میزبان و گواهی سرور اجباری است. درایور فعلی pgx از گزینهٔ `channel_binding=require` در رشتهٔ اتصال پشتیبانی نمی‌کند؛ اتصال خودکار Neon به Vercel که برای این پروژه تنظیم شده این گزینه را ندارد. در صورت استفاده از رشتهٔ اتصال دیگری که این گزینه را الزامی می‌کند، ابتدا درایور را به نسخهٔ پشتیبان channel binding ارتقا دهید، نه اینکه انتظار داشته باشید این نسخه آن را اجرا کند.

محدودکنندهٔ نرخ فعلی از آدرس اتصال ورودی و ایمیل استفاده می‌کند؛ در پشت پراکسی ممکن است چند کاربر یک آدرس مشترک داشته باشند و به محدودیت مشترک برسند. برای ترافیک زیاد، روش شناسایی IP و سیاست محدودسازی باید با تنظیمات پراکسی مورد اعتماد بازبینی شود.

مهاجرت جدید جداول کاربران و نشست‌ها را اضافه می‌کند و جدول پروژه‌های موجود را حذف نمی‌کند. حساب‌های قدیمی OAuth و کوکی‌های آن تبدیل خودکار نمی‌شوند؛ افراد باید حساب جدید داشته باشند. اگر دیتابیس موجودی دارید، پیش از مهاجرت از آن backup بگیرید و بازیابی را آزمایش کنید.

## اجرای داخلی با Docker Compose

Docker Engine و Compose v2 لازم است. `web`، `api` و `db` راه‌اندازی می‌شوند؛ دیتابیس در volume `postgres_data` باقی می‌ماند و در پیش‌فرض فقط پورت وب روی localhost باز است.

```bash
cp .env.example .env
# .env را فقط روی سرور پر کنید: POSTGRES_PASSWORD، PUBLIC_APP_ORIGIN و دو متغیر مدیر اولیه
# سپس پشت reverse proxy دارای HTTPS اجرا کنید:
docker compose up --build -d
docker compose ps
curl -fsS http://127.0.0.1:3000/_health
curl -i http://127.0.0.1:3000/_ready
```

در شبکهٔ داخلی، `DATABASE_URL` بدون رمز و `PGPASSWORD` جداگانه استفاده می‌شوند. اتصال بیرونی PostgreSQL باید TLS و محدودیت شبکه داشته باشد. پس از ایجاد حساب مدیر متغیرهای bootstrap را از `.env` حذف و API را بازسازی کنید. برای LAN در صورت نیاز `WEB_BIND` را روی IP خصوصی و firewall را روی شبکهٔ مجاز تنظیم کنید. هرگز فایل `.env` را commit نکنید.

```bash
git pull
docker compose up --build -d
```

`docker compose down` volume را نگه می‌دارد؛ **از `docker compose down -v` استفاده نکنید** مگر اینکه حذف دیتابیس عمداً خواسته شده باشد.

## پشتیبان‌گیری

Volume پشتیبان جداگانه نیست. backup رمزنگاری‌شده را در محل مستقل نگه دارید و بازیابی را روی دیتابیس آزمایشی تمرین کنید. نمونهٔ dump دستی Compose:

```bash
mkdir -p backups
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' | gzip > "backups/postgres-$(date +%F-%H%M).sql.gz"
```

برای سرویس مدیریت‌شده، محدودیت retention و امکان restore را متناسب با طرح انتخابی کنترل کنید. هنگام بازیابی، API را متوقف و هدف بازیابی را پیش از اجرای مجدد بررسی کنید.
